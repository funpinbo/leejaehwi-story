# Control Plane 단계적 전환과 운영 사고 — shadow → 안전망 → strict → intent

> **한 줄 요약**: chatbot이 다른 서비스를 직접 호출하던 구조를 Control Plane 경유로 바꾸면서, 한 번에 갈아끼우지 않고 **① shadow(복사본만 보내 비교) → ② 안전망 있는 전환(실패 시 직접 호출로 폴백) → ③ 안전망 제거(strict) → ④ 선언형 intent** 4단계로 옮겼습니다. ③에서 배포 수 분 만에 운영 사고가 났고, 원인은 **아무도 쓰지 않는 옛 경로를 설명하는 주석 하나**였습니다.

---

## 1. 상황

- chatbot → 규칙 서비스 / 검색 서비스 / 규격 분석 서비스 / 렌더 서비스 직접 HTTP 호출
- 목표(TASK-1): 카탈로그에 등록된 **모든 호출이 업무 intent를 선언해 Control을 거쳐** 가도록
- 관련 서비스가 많아 한 번에 바꾸면 어디서 깨졌는지 알 수 없음

## 2. 전환 4단계

| 단계 | 모드 | 동작 | 위험 |
|---|---|---|---|
| ① | `shadow` | 실제 응답은 직접 호출, Control에는 **복사본**을 보내 응답을 비교 | 0 — 신호만 수집 |
| ② | `control_with_direct_fallback` | 실제 트래픽이 Control 경유, **실패하면 직접 호출로 폴백** | 낮음 |
| ③ | `control` (strict) | 카탈로그 라우트는 폴백 없음, **카탈로그에 없는 라우트는 fail-closed** | 숨은 경로가 드러남 |
| ④ | intent | 호출자가 `{service, action}` 대신 `{intent, inputs}`만 보냄 | — |

- 각 단계는 **mock이 아니라 실제 서비스 트래픽으로 배포 · 검증한 뒤** 다음 단계로 넘어갔습니다.
- 장시간 비동기 action, 바이너리 payload, GPU 추론처럼 아직 계약이 없는 라우트는 안전망을 **명시적으로 남기고**, "제거 순서가 있는 범위 지정된 갭"으로 추적했습니다.

## 3. 운영 사고

```
③ strict 배포 → 수 분 뒤
GET /v1/blocks/search (규격 분석 서비스, 특정 research 경로)
  → 예전: 조용히 direct 폴백
  → 지금: "카탈로그에 없는 라우트" 오류
```

**근본 원인**

1. 그 호출부는 함수 파라미터로 Control 라우팅을 고르게 하는 **두 번째, 더 오래된 메커니즘**을 거치고 있었음
2. 그런데 실제로 그 파라미터를 설정하는 호출자는 **하나도 없었음** → 그동안 계속 조용히 direct로 감
3. 범용 adapter의 라우트 테이블 주석이 "이 라우트는 두 번째 메커니즘이 처리하니 카탈로그 등록이 필요 없다"고 **잘못 가정**
4. strict 모드가 그 가정이 낡았다는 것을 드러냄

**수정**

- 아무도 안 쓰는 경로를 설명하는 주석을 믿지 않고, **실제 트래픽을 처리하는 한 곳(범용 adapter)에 라우트를 정식 등록**
- 그 라우트가 Control을 거쳐 해석된다는 것을 단언하는 **회귀 테스트** 추가
- 전체 테스트 통과 → 배포 → 운영 로그에서 오류 소멸 확인

## 4. 배운 점

- **큰 전환은 "위험 0인 관찰"부터 시작한다.** shadow 모드는 실제 응답에 영향 없이 차이를 모아 줍니다.
- **안전망은 문제를 숨긴다.** 폴백이 있는 동안에는 "카탈로그에 없는 라우트"가 영원히 보이지 않았습니다. 그래서 안전망 제거는 별도 단계로, 감시와 함께 해야 합니다.
- **주석은 코드가 아니다.** 주석이 설명하던 메커니즘은 아무도 쓰지 않고 있었습니다. 판단은 실제 트래픽 경로 기준으로 합니다.
- **남겨 둔 갭은 이름을 붙여 추적한다.** "아직 폴백이 있다"를 방치가 아니라 제거 순서가 있는 목록으로 관리했습니다.

---

## 예제 코드 — `staged_migration.py`

4단계 모드를 가진 호출 adapter를 만들고, **"아무도 설정하지 않는 옛 파라미터 때문에 카탈로그에서 빠진 라우트"** 를 일부러 넣어 둡니다.
shadow와 fallback 단계에서는 문제가 보이지 않다가, strict 단계에서 드러나고, 수정 + 회귀 테스트 후 해소되는 흐름을 재현합니다.

```bash
python staged_migration.py
```

# LLM은 경계만 판단 — 원문을 다시 쓰지 않는 청킹

> **한 줄 요약**: 사내 문서를 RAG용으로 자를 때 LLM에게 "요약된 청크"를 만들게 하지 않고, **어디서 자를지(경계 인덱스)만** 고르게 했습니다. 청크는 항상 원문 그대로라 **인용이 원문과 글자 단위로 일치**하고, LLM이 연속으로 실패하면 문자 수 규칙으로 자동 폴백합니다.

---

## 1. 상황

- 사내 파일 서버에 있는 사내 문서(PDF · DOCX · XLSX)를 매시간 스캔해 chatbot의 RAG 지식으로 넣는 파이프라인을 만들었습니다.
- 고정 길이로 자르면 표나 조항 중간이 잘리고, LLM으로 "의미 단위 정리"를 시키면 **원문이 바뀝니다.**

## 2. 문제

| 방식 | 문제 |
|---|---|
| 고정 길이 청킹 | 조항 · 표 · 목록이 중간에 잘림 → 검색 품질 저하 |
| LLM이 청크를 다시 작성 | 요약 · 표현 변경 · 누락 → **인용한 문장이 원문에 없음**. 승인 문서 근거로 쓸 수 없음 |

## 3. 설계

```
원문 텍스트 ─▶ ~3,500자 윈도우 ─▶ LLM: "이 윈도우에서 의미가 끊기는 위치의 문단 번호만 JSON으로"
                                  │
                                  ├─ 유효한 인덱스 → 그 위치에서 원문을 자름 (텍스트는 손대지 않음)
                                  └─ 잘못된 응답 → 재시도, 연속 3회 실패 → 문자 수 규칙으로 폴백
```

| 결정 | 이유 |
|---|---|
| **LLM 출력 = 경계 인덱스만** | 원문 보존이 구조적으로 보장됨. 검증도 "인덱스가 범위 안인가, 증가하는가"로 단순 |
| 윈도우 ~3,500자 | 모델 컨텍스트 · 응답 지연 · 경계 판단 품질의 균형 |
| **연속 3회 실패 시 규칙 폴백** | 모델 장애가 파이프라인 전체를 멈추지 않게 |
| `doc_id` = 사내 파일 서버 파일의 고유 ID | 재청킹하면 chatbot 쪽 청크를 **문서 단위로 통째 교체** → 남는 조각 없음 |
| 부서 태그 | 청크마다 부서 코드를 붙이고, 검색과 원문 다운로드 **양쪽에서** 같은 조건으로 재검사 |

## 4. 결과

- 청크를 이어 붙이면 원문과 **완전히 같음** (자동 검증 가능)
- LLM 장애 시에도 배치가 멈추지 않고 규칙 기반 청크로 진행

## 5. 배운 점

- **LLM에게 "쓰게" 하지 말고 "고르게" 한다.** 선택형 출력은 검증이 쉽고, 실패해도 원문이 오염되지 않습니다.
- **불변 조건을 코드로 검사한다.** `"".join(chunks) == original` 한 줄이 "환각 없음"을 증명합니다.
- 모든 LLM 호출에는 **폴백 경로**가 있어야 배치 시스템이 됩니다.

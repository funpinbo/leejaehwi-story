# CronJob 사고를 검사기로 — 사고를 규칙으로, 규칙을 코드로

> **한 줄 요약**: 한정된 GPU를 여러 작업이 나눠 쓰도록 **주간에는 대화형 추론 모델, 야간에는 배치용 비전 모델**을 띄우는 시간대 전환을 CronJob으로 운영했습니다. 그 과정에서 **타임존 해석 오류**와 **파드 라벨 누락으로 인한 네트워크 차단** 사고를 겪었고, 둘 다 CronJob 표준 규칙과 검사 코드로 만들었습니다.

---

## 1. 상황

- GPU가 넉넉하지 않아 대화형 모델과 야간 배치(OCR 등)용 모델을 **동시에 띄울 수 없었습니다.**
- 그래서 사용 패턴에 맞춰 **시간대로 나눴습니다.** 주간에는 사용자 대화, 야간에는 배치 처리.
- 전환은 정해진 시각에 CronJob이 서빙을 올리고 내리는 방식입니다.

## 2. 사고 ① — 타임존

| 의도 | 실제 |
|---|---|
| UTC 기준이라 생각하고 KST 시각을 UTC로 환산해 schedule 작성 | 클러스터는 `timeZone`이 없으면 **서버 로컬(KST) 숫자 그대로** 해석 → 엉뚱한 시각에 발동 |
| 아침에 야간 작업 종료 | 종료 Job이 **밤에** 발동 → 야간 배치 도중 GPU 서빙이 내려감 |

**규칙**: 모든 CronJob에 `timeZone: Asia/Seoul`을 **필수**로 쓰고, schedule은 **KST 벽시계 숫자 그대로** 적는다.

## 3. 사고 ② — 라벨 누락

- 네트워크 정책이 기본 차단(default-deny)이고, 허용은 **파드 라벨**로 지정돼 있었습니다.
- 새 CronJob 파드에 서비스 라벨을 빼먹어 **모든 외부 통신(쿠버네티스 API 포함)이 차단** → 매 실행 100% 실패.

**규칙**: CronJob 파드에도 서비스 라벨(`app.kubernetes.io/name`)과 `component`를 붙여 네트워크 정책 셀렉터와 일치시킨다. 이 라벨이 없으면 로그 수집도 되지 않는다.

## 4. CronJob 표준 (사고에서 나온 규칙)

| 규칙 | 이유 |
|---|---|
| `timeZone: Asia/Seoul` 필수 | 사고 ① |
| `concurrencyPolicy: Forbid` | 이전 실행이 끝나기 전 겹치지 않게 |
| `backoffLimit: 0` | 재시도는 Job이 아니라 **다음 주기**가 담당 (작업은 멱등) |
| `activeDeadlineSeconds` **< 다음 주기** | 장시간 작업이 다음 실행을 침범하지 않게 (필요하면 1회 처리량을 줄임) |
| 서비스 라벨 필수 | 사고 ② |
| CronJob은 **배포 저장소에 커밋** | GitOps — 클러스터에서 직접 만들지 않음 |
| GPU 전환 스케줄 추가 시 **기존 시간대와 충돌 검토** | 전환이 "마지막 요청이 이긴다" 구조라 겹치면 서로를 내림 |

## 5. 남은 과제 (정직하게)

- 시간대 정의가 **CronJob과 워커 코드 두 곳에 중복** → 한쪽만 바꾸면 어긋남. 단일 정의로 모으는 것이 다음 과제.
- 여러 작업이 GPU 서빙을 직접 스케일 → 동시 전환 시 충돌 가능. 단일 스케줄러(lease) 도입 검토.

## 6. 배운 점

- **사고는 사람의 기억이 아니라 규칙과 검사기로 남긴다.** "다음엔 조심하자"는 다음 사람에게 전달되지 않습니다.
- **암묵적 기본값을 믿지 않는다.** 타임존처럼 "당연히 이렇겠지" 하는 값은 반드시 명시합니다.
- **공유 자원은 시간으로 나누는 것도 설계다.** 자원을 늘리기 전에 사용 패턴에 맞춰 나눌 수 있는지 봅니다.

---

## 예제 코드 — `cronjob_lint.py`

CronJob 정의(dict)를 위 표준으로 검사하는 린터입니다. 사고 ①(타임존 누락) · ②(라벨 누락)와 실행 시간 초과, 시간대 정의 불일치를 잡아냅니다. 시각 · 이름은 모두 예시이고, 의존성 없이 실행됩니다.

```bash
python cronjob_lint.py
```

# project_ai_dlc_memory_system — AI 협업 개발 워크플로우

> 이 문서는 이 프로젝트에서 AI 협업 작업을 지시하기 위해 실제로 쓴 내부 프로세스 문서와 같은 형식(버전 헤더, 번호가 매겨진 섹션, 문서 템플릿)으로 작성됐다 — 그 형식을 설명하는 글이 아니라, 그 형식 자체를 일반화해서 그대로 재현한 것이다. 이 프로세스로 만들어진 시스템 자체는 [01-architecture.md](01-architecture.md) 참고.

---

## 0. 왜 이게 필요한가

세션 사이에 지속되는 기억이 없는 AI 코딩 에이전트는 호출될 때마다 맥락을 다시 도출해야 하는데, 프로젝트가 여러 서비스와 여러 개의 동시 작업 흐름에 걸치게 되면 이건 느리고 일관성이 없어진다. 조직화하는 핵심 아이디어: **"왜/무엇을"(드물고 신중하게 바뀜)과 "지금 당장 뭘"(계속 버려지고 다시 만들어짐)을 분리하고**, 각각에 자기만의 문서를 줘서, 에이전트가 행동하기 전에 실제로 필요한 작은, 지금의 조각만 로드하면 되게 한다 — 매번 프로젝트 전체 역사를 다시 읽을 필요가 없게한다.


## 1. 문서 계층

| 문서 | scope | 수명 | 묻는 질문 |
|---|---|---|---|
| `plan` | 서비스 또는 프로젝트 전체 | 드물고 신중하게 바뀜 | 이 서비스의 설계는 무엇이고, 왜 그런가? |
| `rule` | 서비스 또는 프로젝트 전체 | 드물게 바뀜 | 모든 변경이 지켜야 하는 제약은 무엇인가? |
| `prompt` 큐 | 서비스 | 영구, 누적 기록 | 사람이 자기 말로 뭘 요청했는가? |
| `log` | 서비스 | 영구, 누적 기록 | 뭘 끝냈고, 어떻게 확인했는가? |
| **`task`**  | 서비스 통합, 작업 단위 | 그 task가 끝날 때까지 | 지금 끝내려는 것은 무엇이고, 누가 어느 부분을 맡는가? |
| **long-term memory** | 서비스 , 지금 task 기준 | task가 끝나거나 `plan`이 바뀔 때까지 | 지금 task를 끝내려면 이 서비스가 할 일 목록은 순서대로 무엇인가? |
| **short-term memory**  | 서비스 | 지금 항목이 끝날 때까지 | 구체적으로, 지금 당장 뭐가 일어나는가? |

`plan`/`rule`/`prompt`/`log`는 원래부터 있던 안정적인 뼈대다. `task`, long-term memory, short-term memory는 `plan`을 실제로 실행되는 단계들의 순서로 바꾸는 계층이다. 가장 중요한 구분: **`plan`을 바꾸는 것은 그 자체로 기록할 가치가 있는 결정이고; long-term memory를 다시 쓰는 건 그 plan을 실행하기 위한 오늘의 체크리스트일 뿐이며, 계속 바뀌는 게 당연하다.**

## 2. 문서 템플릿

### 2.1 `task` (서비스 통합)

```markdown
## TASK-<번호>: <한 줄 제목>

- 상태: 진행중 | 보류 | 완료
- 관련 서비스: service-a, service-b, ...
- 완료 기준: <구체적이고 확인 가능한 완료 조건>
- 서비스별 분담:
  - service-a: <이 서비스가 맡은 부분 한 줄 요약> — 상세는 service-a의 long-term memory 참고
  - service-b: <...>
- 진행 로그: 서비스별 진행 상황이 바뀔 때마다 한 줄씩(날짜 + 무엇이 끝났는지) — 전체 그림용, 상세 기록은 각 서비스 자체 log에 있다.
```

### 2.2 long-term memory (서비스 하나, 지금 task 기준)

```markdown
# <service> long-term memory — TASK-<번호>

> TASK-<번호>가 끝나거나 범위가 바뀌면 다시 채워진다. 설계 이유는 여기 안 적는다 — 그건 `plan`의 역할이다.

1. [ ] <할 일 1> — 완료 기준: <...>
2. [ ] <할 일 2> — 완료 기준: <...>
3. [ ] <할 일 3> — 완료 기준: <...>
```

### 2.3 short-term memory (서비스 하나; 항상 아래 세 상태 중 정확히 하나)

```markdown
# <service> short-term memory

## 지금 할 일
- long-term memory 항목: #2 — <할 일 2>
- 구체적 다음 행동: <지금 바로 실행할 수 있는 수준까지 쪼갠 것>
- 시작 시각: YYYY-MM-DD HH:MM
```

```markdown
# <service> short-term memory

## 비어 있음
long-term memory 2번 항목을 끝내고 log에 기록했다. 다음 항목은 아직 안 뽑았다 — hook이 곧 채울 것이다.
```

```markdown
# <service> short-term memory

## 막힘 — 사람의 결정 필요
- long-term memory 항목: #2 — <할 일 2>
- 막힌 이유: <구체적으로 — 설계 결정 필요 / 승인 필요 / 외부 의존성 등>
- 사람에게 묻고 싶은 것: <...>
```

## 3. 실행 순환

```
1. 행동하기 전에 에이전트는 그 서비스의 short-term memory만 읽는다 — plan 전체도, long-term
   memory 목록 전체도 아니다. 그 파일에는 지금 당장 할 일 하나만 들어 있다.
2. 에이전트가 그 하나를 수행한다.
3. 완료되면:
   a. 그 서비스의 log에 결과를 append (뭘 했고 어떻게 확인했는지)
   b. 서비스 통합 task 문서에 한 줄 진행 업데이트 추가
   c. short-term memory를 "비어 있음"으로 바꾼다
4. 에이전트의 턴이 끝나는 지점에서 발동되는 hook이 short-term memory가 막 "비어 있음"이 됐는지 확인한다:
   - long-term memory에 아직 안 끝난 항목이 있으면 → 다음 항목을 "지금 할 일"로 가져온다
   - long-term memory가 소진됐으면 → 이 서비스가 맡은 task 부분을 완료로 표시한다
   - 다음 단계가 사람의 판단이 필요하면 → 대신 "막힘"을 쓰고 멈춘다; 순환을 계속 돌리려고
     조용히 다음 할 일을 지어내는 일은 절대 없다
5. 반복한다. 관련된 모든 서비스가 자기 몫을 완료로 표시하면 task가 끝난다.
```

이 hook은 long-term memory와 task 문서를 실제로 읽고 다음이 뭔지 판단해야 한다 — 이건 단순 파일 존재 확인이 아니라 판단이 필요한 일이므로, 평범한 스크립트가 아니라 작은 agent 타입 hook으로 구현한다. 의도적으로 보수적으로 동작한다: 이전 항목이 깨끗하게 끝났을 때만 short-term memory를 다시 채우고, 문서 생성 에이전트 자체가 추측하는 대신 멈추도록 만들어진 바로 그 판단 지점에서 똑같이 멈춘다([03-agent.md](03-agent.md) 참고).

## 4. 서로 보완하는 두 skill

- **라우팅** — 요청이 어떤 서비스의 prompt 큐에 적히면, 가장 먼저 할 일은 이걸 실제로 처리해야 할 서비스가 어디인지 판단하는 것이다 — 증상이 발견된 서비스가 항상 그 서비스는 아니기 때문이다. 작고 한 번에 끝나는 수정은 그 자리에서 바로 처리되고 결과가 prompt 큐에 다시 기록된다. 다단계거나 서비스 횡단인 요청은 그 자리에서 처리하는 대신 아래 memory cycle로 넘긴다.
- **Memory cycling** — 요청이 다단계라고 판단되면, `task`와 관련 서비스마다의 long-term memory를 만들고, 관련된 모든 서비스가 끝날 때까지 §3의 순환을 돌린다.

```
요청이 prompt 큐에 적힘
        │
        ▼
  라우팅: 실제로 이걸 처리해야 할 서비스는 어디인가?
        │
        ├─ 작고 한 번에 끝나는 수정 ─────────→ 그 자리에서 처리, 결과를 prompt 큐에 기록
        │
        └─ 다단계 / 서비스 횡단
                │
                ▼
         memory cycle: TASK 생성(또는 합류), 관련 서비스마다 long-term memory 채움
                │
                ▼
         short-term memory ← long-term memory ← 실행 순환(§3) → log
```

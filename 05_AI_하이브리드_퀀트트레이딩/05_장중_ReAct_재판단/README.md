# 장중 ReAct 재판단 — 검색할지 말지도 LLM이 정하게 하기

> **한 줄 요약**: 아침에 세운 매매 계획은 장중 뉴스 한 건으로 무효가 될 수 있어서, 5분마다 보유 종목에 대해 **8개 쿼리 × 3채널을 병렬 검색**하고, LLM이 **추가 검색이 필요한지 스스로 판단하는 ReAct 구조**로 SELL / HOLD / BUY_MORE를 다시 결정하게 했습니다.

---

## 1. 상황

- 매매 Plan은 전날 22:00에 만들어집니다. 하지만 장중에 공시·수주 뉴스가 나오면 계획의 전제가 바뀝니다.
- 사람이 장중에 뉴스를 계속 볼 수 없으므로, **보유 종목을 주기적으로 다시 판단**하는 장치가 필요했습니다.

## 2. 문제

| 문제 | 설명 |
|---|---|
| 검색 시간 | 종목당 수십 건의 검색을 순차로 하면 5분 주기 안에 끝나지 않음 |
| 고정 파이프라인의 낭비 | "항상 검색 → 항상 판단"은 뉴스가 없는 종목에도 같은 비용 |
| 판단 근거 부족 | 첫 검색 결과가 애매하면 추가 확인이 필요 |

## 3. 설계

```
5분 주기 (APScheduler)
  └ 보유 종목마다
      Thought  : 지금 상황에서 무엇을 확인해야 하는가?
      Action   : search(쿼리)  또는  decide(SELL | HOLD | BUY_MORE)
      Observation : 검색 결과
      ... 반복 (최대 단계 초과 시 HOLD로 안전 종료)
```

| 결정 | 이유 |
|---|---|
| **8 쿼리 × 3 채널(뉴스·블로그·웹) 병렬** | `asyncio.gather`로 동시에 → 순차 대비 검색 시간이 가장 느린 요청 하나 수준으로 |
| **ReAct** (Reason + Act) | 검색 여부와 추가 검색 쿼리를 LLM이 판단 → 근거가 충분하면 바로 결정, 애매하면 한 번 더 확인 |
| **최대 단계 + 안전 기본값** | 루프가 길어지거나 실패하면 HOLD — 자동매매에서 "모르면 아무것도 하지 않는다" |

## 4. 결과

- 5분 주기 안에 보유 종목 재판단 완료
- 판단마다 Thought · Observation 기록이 남아, **왜 그 결정을 했는지 사후 추적** 가능

## 5. 배운 점

- **에이전트에게 "행동 선택권"을 줄 때는 반드시 상한과 기본값을 같이 준다.** 자동매매처럼 실행이 돈과 연결되는 시스템에서 안전한 기본 동작은 설계의 일부입니다.
- **I/O 대기는 병렬로.** LLM 시스템의 지연은 모델 추론보다 외부 검색·API 대기에서 더 많이 생깁니다.
- 이 경험은 사내 프롬프트 엔지니어링 교육에서 ReAct를 설명할 때 실제 사례로 썼습니다.

---

## 🧪 예제 코드 — `intraday_react.py`

검색 API와 LLM을 대역 함수로 대체해, 병렬 검색과 ReAct 루프(Thought → Action → Observation → decide)를 재현합니다.

```bash
python intraday_react.py
```

```
[09:35 재판단] 067310 하나마이크론 (보유, 장중 +6.2%)
  Thought 1: 보유 중인데 장중 급등. 원인 뉴스가 있는지 먼저 확인해야 한다.
  Action  1: search 8쿼리 × 3채널 = 24건 병렬 (0.05s)
    Observation: [news] 하나마이크론 수주: 대형 고객사 패키징 수주 확대 보도
    Observation: [news] 하나마이크론 공시: 단일판매·공급계약 체결 공시
  Thought 2: 수주 보도와 공급계약 공시가 모두 확인됨. 급등 근거가 있다.

결정: {'code': '067310', 'decision': 'BUY_MORE', 'confidence': 0.68}
(순차 실행이었다면 검색에만 약 1.2s 이상)
```

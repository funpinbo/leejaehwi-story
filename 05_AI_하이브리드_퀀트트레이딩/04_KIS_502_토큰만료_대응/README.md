# KIS 502 토큰 만료 대응 — 에러 코드를 믿지 말고 원인을 확인하기

> **한 줄 요약**: 토큰이 만료되면 401이 올 거라 생각하고 만든 재시도 로직이 무의미했습니다. 실제로는 **502(Bad Gateway)** 가 오는 경우가 있었고, 502를 받으면 같은 요청을 반복하는 대신 **토큰을 강제로 갱신한 뒤 재시도**하도록 바꿨습니다.

---

## 1. 상황

- 09:06 자동 주문은 KIS REST API로 실행됩니다. 접근 토큰에는 유효기간이 있습니다.
- 처음 구현: 401(Unauthorized)이면 토큰 갱신, 5xx면 "서버 일시 오류"로 보고 같은 요청을 재시도.

## 2. 문제

- 간헐적으로 **주문이 재시도 끝에 전부 실패**하는 날이 있었습니다.
- 재시도를 아무리 늘려도 해결되지 않았습니다.

## 3. 원인 분석

| 확인한 것 | 결과 |
|---|---|
| 실패 시점의 응답 로그 | 401이 아니라 **502** |
| 실패 직전 토큰 발급 시각 | 대부분 **유효기간 경과 직후** |
| 토큰만 수동 갱신 후 같은 요청 | 바로 성공 |

→ **토큰 만료가 502로 표현되는 경우가 있다.** 같은 토큰으로 재시도하면 영원히 실패합니다.

## 4. 해결

```
요청 → 401           → 토큰 갱신 → 1회 재시도
     → 502           → 토큰 "강제" 갱신 → 재시도      ← 추가
     → 그 외 5xx      → 지수 백오프 재시도 (최대 N회)
     → 성공           → 반환
+ 만료 시각 이전에 미리 갱신(선제 갱신)
```

## 5. 결과

- 토큰 만료로 인한 주문 실패 해소
- "재시도 = 같은 요청 반복"이 아니라 **"원인별로 다른 복구 동작"** 으로 재시도 정책을 재정리

## 6. 배운 점

- **에러 코드는 원인이 아니라 증상이다.** 응답 코드만 보고 분기하면, 외부 시스템이 비표준 동작을 할 때 복구 로직이 무력해집니다. 실패 시점의 상태(토큰 발급 시각)를 함께 로그로 남겨야 원인을 찾을 수 있습니다.
- **재시도는 상태를 바꿀 때만 의미가 있다.** 같은 입력으로 같은 요청을 반복하는 재시도는 일시 장애에만 효과가 있습니다.
- 다음 단계로, KIS API 장애로 주문 자체가 유실되지 않도록 메시지 큐 기반 구조를 검토하고 있습니다.

---

## 예제 코드 — `token_refresh_retry.py`

토큰이 만료되면 502를 돌려주는 **가짜 KIS 서버**를 만들고, 기존 재시도 정책(같은 요청 반복)과 개선된 정책(502 → 토큰 강제 갱신)을 비교합니다.

```bash
python token_refresh_retry.py
```

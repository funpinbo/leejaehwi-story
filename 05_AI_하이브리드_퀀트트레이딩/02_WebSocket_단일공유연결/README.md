# WebSocket 단일 공유 연결 — 외부 시스템의 제약에 구조를 맞추기

> **한 줄 요약**: 종목마다 WebSocket을 따로 열었더니 연결이 계속 끊겼고, 원인이 "KIS는 approval_key 하나당 연결 1개만 허용"이라는 제약임을 확인한 뒤 **단일 연결 + 콜백 딕셔너리 라우팅 + 자동 재연결** 구조로 전면 리팩터링해 연결 장애를 약 90% 줄였습니다.

---

## 1. 상황

- 장중 실시간 시세·체결 데이터를 받기 위해 한국투자증권(KIS) WebSocket을 사용합니다.
- 처음에는 **보유 종목마다 별도의 WebSocket 연결**을 열고, 각 연결이 자기 종목 데이터를 처리하는 구조였습니다.

## 2. 문제

- 종목이 늘어날수록 연결이 서로를 끊어내며 **CRITICAL 로그가 반복**되었습니다.
- 데이터가 끊기면 장중 재판단(5분 주기)이 오래된 가격으로 판단하게 됩니다.

## 3. 원인 분석

| 확인한 것 | 결론 |
|---|---|
| 끊김이 종목 수와 비례 | 개별 코드 버그보다 **연결 수 자체**가 문제 |
| KIS 공식 문서·예제 재확인 | **approval_key당 WebSocket 연결은 1개만 허용** |
| 모의투자 연결 포트 | 문서상 포트가 아니라 **실전 포트(21000)** 를 써야 동작 (공식 예제로 확인) |

## 4. 해결 — 단일 공유 연결

```
              ┌──────────── 단일 WebSocket ────────────┐
구독 요청 →   │ subscribe(code, callback)              │
              │ callbacks = {                          │
              │   "036540": [plan_monitor, logger],    │   수신 메시지
              │   "067310": [plan_monitor],            │ ← 종목코드 파싱 → 해당 콜백만 호출
              │ }                                      │
              │ 끊김 감지 → 지수 백오프 재연결          │
              │ 재연결 후 callbacks 키 전체 재구독      │
              └────────────────────────────────────────┘
```

- **연결은 하나, 라우팅은 딕셔너리**: 수신 메시지의 종목코드로 등록된 콜백만 호출
- **자동 재연결**: 끊김 감지 시 지수 백오프(1s → 2s → 4s …)로 재연결
- **구독 상태 복구**: 재연결 후 콜백 딕셔너리에 있는 종목을 모두 다시 구독 → 호출하는 쪽은 끊김을 몰라도 됨

## 5. 결과

- 연결 장애(CRITICAL 로그) **약 90% 감소**
- 종목 추가·삭제가 `subscribe` / `unsubscribe` 한 줄로 단순해짐

## 6. 배운 점

- **외부 시스템의 제약을 먼저 확인한다.** 코드를 고치기 전에 "상대가 무엇을 허용하는가"를 확인했으면 처음부터 맞는 구조로 만들었을 것입니다.
- **문서보다 공식 예제와 실제 응답이 진실이다.** 포트 문제도 문서가 아니라 공식 예제 코드에서 찾았습니다.
- **복구는 호출자가 아니라 연결 계층이 책임진다.** 재연결과 재구독을 한곳에 모으니 나머지 코드가 단순해졌습니다.

---

## 예제 코드 — `shared_websocket.py`

실제 KIS 서버 대신 **가짜 서버**(일정 시간마다 연결을 끊음)를 붙여, 단일 연결 · 콜백 라우팅 · 자동 재연결 · 재구독을 `asyncio`로 재현합니다.

```bash
python shared_websocket.py
```

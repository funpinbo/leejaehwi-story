# 역할 분리 에이전트 설계 — 쓰는 에이전트, 맞추는 에이전트, 의심하는 에이전트

> **한 줄 요약**: 하나의 LLM이 "내용 작성 + 형식 맞추기 + 사실 확인"을 모두 하면 어디서 틀렸는지 알 수 없어서, **Report / Layout / Verification** 세 에이전트로 책임을 나누고, 모든 값에 **근거(source)** 를 붙이도록 설계했습니다.

---

## 1. 상황

- 템플릿 엔진으로 형식 문제는 해결했지만, 내용 쪽에 새로운 위험이 보였습니다.
- PAD에는 **규격 번호와 Revision**이 들어가는데, LLM은 학습 시점의 오래된 Revision을 자신 있게 적을 수 있습니다. 승인 문서에서 이는 치명적입니다.

## 2. 설계

| 에이전트 | 책임 | 출력 |
|---|---|---|
| **Report Agent** | 목적 분석, 데이터 검색, 규격 참조, 내용 생성 | 값 + **근거(source)** |
| **Layout Agent** | 템플릿 구조 분석, placeholder ↔ 내용 키 정합성, 지정 위치 삽입 | 누락/잉여 키 보고 → 템플릿 엔진 |
| **Knowledge · Verification Agent** | 규격 번호 · Revision 확인, 근거 데이터 추적 | 불일치 수정 또는 **사람 검토 요청** |

```
Report Agent ──(값+근거)──▶ Layout Agent ──▶ Verification Agent ──▶ 템플릿 엔진 ──▶ 문서
                                                    │
                                                    └─ 근거가 "LLM 지식"뿐인 값 → 사람 검토
```

## 3. PAD 스키마 — 양방향 교차 검증 (검토)

- **Top-down**: ECSS 규격에서 PAD에 필요한 항목을 뽑아 JSON 스키마로 정의
- **Bottom-up**: 이미 작성된 PAD 문서들을 GPT-OSS-120B로 같은 스키마에 역분해
- 두 결과를 비교해 "규격엔 있는데 실제 문서엔 없는 항목", "실제 문서엔 있는데 스키마에 없는 항목"을 찾아 스키마를 보완하는 구조

## 4. 결과

- 값마다 근거가 붙어 있어, 검토자가 **"이 값은 어디서 왔나"** 를 바로 확인 가능
- Revision처럼 LLM이 틀리기 쉬운 값은 레지스트리로 검증하고, 근거가 약한 값은 사람에게 넘기는 흐름 설계

## 5. 배운 점

- **에이전트를 나누는 기준은 "검증 방법"이다.** 내용은 근거로, 형식은 템플릿 정합성으로, 사실은 레지스트리로 — 검증 방법이 다르면 책임도 나눕니다.
- **LLM 출력에는 출처를 붙인다.** 출처가 "LLM 지식"뿐인 값은 기본적으로 의심합니다. 이 관점이 ECSS 프로젝트의 `sources`, `confidence`, `requires_review` 필드로 이어졌습니다.

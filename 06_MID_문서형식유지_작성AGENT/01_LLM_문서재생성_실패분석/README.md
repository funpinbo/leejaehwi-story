# LLM 문서 재생성 실패 분석 — 실패를 분류하면 원인이 보인다

> **한 줄 요약**: qwen2.5-vl-7b, qwen3.6-35b로 "기존 Word 템플릿에 내용만 바꿔 다시 생성"하는 실험을 했고, 머리글 · 폰트 · numbering · 들여쓰기 등 9가지 유형의 레이아웃 붕괴를 정리한 끝에 **"LLM에게 문서 생성 전체를 맡기는 방식 자체가 불안정하다"** 고 결론 내렸습니다.

---

## 1. 상황

- 목표: 기존 PAD Word 템플릿에, 새 부품의 데이터·규격 내용을 채워 넣은 문서를 자동으로 만드는 것.
- 초기 가설: "멀티모달/대형 LLM이라면 문서를 보고 같은 형식으로 내용만 바꿔 다시 만들 수 있을 것이다."

## 2. 시도

- qwen2.5-vl-7b (비전-언어), qwen3.6-35b로 템플릿 문서 + 새 내용을 주고 문서를 다시 생성

## 3. 실제로 발생한 문제 (분류)

| # | 유형 | 실제 현상 |
|---|---|---|
| 1 | 머리글 | 머리글 이미지 · 제목 **위치 오류** |
| 2 | 바닥글 | 바닥글 **중복 삽입** |
| 3 | 정렬 | 불필요한 **중앙 정렬**로 변경 |
| 4 | 폰트 | 맑은 고딕 → **Noto Sans CJK KR**로 임의 변경 |
| 5 | 글자 크기 | 10pt → **10.5pt** |
| 6 | 번호 매기기 | Word numbering이 **일반 텍스트 "1."** 로 깨짐 |
| 7 | 들여쓰기 | 들여쓰기 정보 **소실** |
| 8 | 위치 | 특정 위치를 **교체**해야 하는데 **append** 됨 |
| 9 | 블록 병합 | 서로 다른 정렬의 블록이 **잘못 merge** 됨 |

## 4. 원인 분석

- 프롬프트를 고쳐 하나를 막으면 다른 것이 깨졌습니다. 개별 버그가 아니라 **방식의 문제**라는 신호였습니다.
- Word 문서의 형식은 텍스트가 아니라 **XML 구조 · 스타일 정의 · numbering 정의 · section 속성**에 있습니다. LLM은 이것을 "다시 써야" 하는데, 이 과정은 본질적으로 **비결정적**입니다.
- 레이아웃은 **매번 똑같아야 하는 것(결정적)**, 내용은 **매번 달라지는 것(비결정적)** → 둘을 같은 생성 과정에 넣은 것이 근본 원인.

## 5. 결론 → 다음 설계

```
"LLM이 문서를 만든다"  (X)
"LLM은 내용을 만들고, 문서는 코드가 만든다"  (O)
```

→ [02. Content / Layout 분리 템플릿 엔진](../02_Content_Layout_분리_템플릿엔진)

## 6. 배운 점

- **실패는 분류해야 원인이 보인다.** 증상 9개를 표로 정리하자 공통점(모두 형식 정보)이 드러났습니다.
- **비결정적인 도구에 결정적인 일을 맡기지 않는다.** 이후 모든 LLM 시스템 설계에서 "이 부분은 매번 같아야 하는가?"를 먼저 묻습니다.
- **비교 가능한 검증 도구를 먼저 만든다.** "깨졌다"는 느낌이 아니라 원본과 결과의 형식 속성을 자동으로 비교해야, 개선 여부를 판단할 수 있습니다.

---

## 예제 코드 — `layout_diff.py`

원본 템플릿과 결과 문서의 **문단 · run 단위 형식 속성**(폰트, 크기, 정렬, 들여쓰기, numbering 스타일, 머리글/바닥글)을 비교해 레이아웃 붕괴를 자동 검출합니다.
예제에서는 "LLM이 텍스트만 보고 문서를 다시 만든" 상황을 재현해 비교합니다.

```bash
pip install python-docx
python layout_diff.py
```

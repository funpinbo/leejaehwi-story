# 결정적 ID로 캐시와 부분 재계산 — 해시 하나가 세 가지 문제를 푼다

> **한 줄 요약**: 데이터 ID를 **입력 데이터 ID · 로직 버전 · 요청 파라미터의 해시**로 정했습니다. 그러자 "같은 요청이면 다시 계산하지 않기", "로직이 바뀐 단계부터만 다시 계산하기", "동시에 들어온 같은 요청은 한 번만 계산하기"가 ID 비교 하나로 해결됐습니다. 대신 **Planner가 미리 계산한 ID와 저장소가 발급한 ID가 반드시 같아야** 해서, 그 등식을 가장 먼저 테스트로 고정했습니다.

---

## 1. 상황

- 챗봇에서는 비슷한 질문이 반복됩니다. 같은 검색 결과에 같은 임베딩을 다시 돌릴 이유가 없습니다.
- 반대로 가공 로직(요약 방식)을 고치면, 검색 · 임베딩은 그대로 두고 **가공부터만** 다시 해야 합니다.
- 여러 서비스가 동시에 같은 결과를 요청하기도 합니다.

## 2. 문제

| # | 문제 | 단순한 방법의 한계 |
|---|---|---|
| 1 | 같은 요청 판별 | 요청 파라미터만 비교하면, 로직이 바뀐 것을 모름 |
| 2 | 부분 재계산 | "어느 단계부터 다시?"를 사람이 정하면 실수함 |
| 3 | 동시 요청 | 같은 계산이 두 번 돌고, 결과가 두 벌 생김 |
| 4 | 계보 | 결과가 어떤 입력에서 나왔는지 따로 기록해야 함 |

## 3. 해결

```
step_key    = hash(서비스, Action, 버전, {슬롯: 입력 artifact_id}, 루트 params)
lineage_key = hash(step_key, 출력 슬롯)
artifact_id = hash(sorted(부모 artifact_id), lineage_key, generation)
```

| 문제 | ID로 푸는 방법 |
|---|---|
| 같은 요청 | 같은 `step_key`의 결과가 hot에 있으면 그 단계를 건너뜀 (`fresh_for`로 유효기간) |
| 부분 재계산 | Action 로직이 바뀌면 버전이 바뀌고 → 그 단계의 `step_key`가 바뀌고 → 출력 ID가 바뀌어 하위 단계도 자연히 새로 계산. **앞 단계는 그대로 재사용** |
| 동시 요청 | 진행 중인 같은 `step_key`가 있으면 새로 만들지 않고 합류 (DB의 부분 유니크 인덱스로 보장) |
| 계보 | 부모 ID가 해시에 들어가므로 ID 자체가 계보를 담음. 엣지 테이블로 역추적 |

- 입력은 **슬롯 이름을 키로 한 매핑**으로 해시합니다. 나열 순서와 무관하고, 같은 데이터가 다른 슬롯에 들어가면 다른 단계가 됩니다.
- params는 **첫 단계에만** 넣습니다. 이후 단계는 입력 ID의 연쇄만으로 정해집니다.
- Planner(실행 전)와 Resolver(저장 후)가 같은 해시를 쓰도록 `ids` 모듈 하나에 모으고, **`planned_id == 발급 id`를 테스트로 고정**했습니다.

## 4. 결과

- 같은 질문을 다시 하면 실행 단계 0개, "캐시: fetch, embed, refine"으로 표시됩니다.
- 가공 로직만 고치고 서비스를 다시 띄우면 가공 단계부터 다시 계산합니다. 주석 · 공백 · docstring만 바뀐 것은 같은 버전으로 봅니다.
- 웹 UI의 실행 상세에서 단계마다 "실행 / 캐시 / 합류"가 구분되어 보입니다.

## 5. 배운 점

- **식별자를 잘 정하면 기능이 따라온다.** 캐시, 부분 재계산, 중복 제거, 계보를 각각 구현하지 않고 ID 정의 하나에서 얻었습니다.
- **두 곳에서 같은 값을 계산해야 하면, 그 등식이 시스템의 급소다.** 그래서 구현 첫 단계에 테스트로 못 박았습니다.
- **"같다"의 기준을 명시해야 한다.** 무엇이 바뀌면 다른 데이터인가(로직 · 입력 · 파라미터)와 무엇은 바뀌어도 같은가(주석 · 순서)를 설계 문서에 먼저 적었습니다.

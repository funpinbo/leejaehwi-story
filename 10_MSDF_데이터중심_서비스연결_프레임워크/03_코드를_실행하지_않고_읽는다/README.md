# 코드를 실행하지 않고 읽는다 — 틀린 것은 실행 전에, 한 번에

> **한 줄 요약**: 어느 Action이 어느 서비스 것인지, 슬롯 선언이 함수 인자와 맞는지, Action의 버전이 무엇인지를 **코드를 import하지 않고 ast로 읽어** 정했습니다. 덕분에 `msdf check` 한 번에 모든 오류를 파일 · 줄 · 원문 · 고칠 방법과 함께 보여 줄 수 있었습니다. 0.2에서는 버전이 Action 본문만 보던 한계를 넘어 **Action이 부르는 프로젝트 안 도우미 코드까지** 따라가게 했습니다.

---

## 1. 상황

- 서비스 코드는 각자 무거운 의존성(DB 드라이버, 모델 등)을 가질 수 있어서, 엔진이 서비스 코드를 import하면 엔진 쪽에도 그 의존성이 필요해집니다.
- 사용자에게 "이 Action은 이 서비스 소속"을 매번 적게 하고 싶지 않았습니다.
- 런타임에 터지는 오류(없는 Action, 틀린 슬롯 이름)는 서비스 여러 개를 띄운 뒤에야 드러납니다.

## 2. 해결

| 판정 | 방법 |
|---|---|
| 서비스 소속 | `service()`가 있는 파일에서 **프로젝트 안 import를 따라가** 닿는 `@action`은 그 서비스 것. 두 서비스가 같은 Action에 닿으면 로딩 오류 |
| 선언 검사 | `inputs` · `params`가 함수 인자에 있는지, 옵션 값이 리터럴인지, 최상위 함수인지 |
| 버전 | 함수 AST를 정규화(주석 · 공백 · docstring · 데코레이터 제거)한 해시 |
| 오류 표시 | 오류를 모아서 한 번에. 파일 · 줄 · 원문 · 이유 · 고칠 방법 |

```text
MSDF 로딩 오류: dags/daily_stats.yaml
  노드 'clean': 서비스 'transform'에 Action 'cleaning'이 없습니다.
  고칠 방법: 있는 Action: clean, summarize
```

## 3. 0.1의 한계와 0.2의 개선

0.1의 버전은 **Action 본문만** 봤습니다. Action이 부르는 `normalize()`를 고쳐도 버전이 그대로라 옛 캐시가 쓰였고, 문서에는 "그럴 때는 `version=`을 직접 올리세요"라고 적어 두었습니다.

0.2에서는 파일마다 최상위 함수 · 클래스 · 상수의 정규화 해시와 그 안에서 참조하는 이름을 모아 두고, Action에서 시작해 **같은 파일의 정의, `from util import f`, `import util` 후 `util.f`** 를 따라가며 닿는 것의 해시를 버전에 더했습니다.

```
Action a ──참조──▶ h() ──참조──▶ K = 2      → 버전 = hash(a 본문, h 해시, K 해시)
          └──▶ util.norm (다른 파일)       → 쓰지 않는 util.other는 영향 없음
```

- 도우미가 없는 Action은 **0.1과 같은 버전**이 나오게 해 기존 캐시를 지켰습니다.
- 클래스 안 메서드에 붙은 `@action`이 최상위 함수로 잘못 처리될 수 있던 버그도 이때 발견해 로딩 오류로 바꿨습니다.
- 분석 결과는 파일별(수정 시각 · 크기 · 버전 기준)로 캐시해, 바뀌지 않은 파일은 다시 읽지 않습니다.

## 4. 배운 점

- **실행하지 않고 판단할 수 있는 것은 실행 전에 판단한다.** 오류를 한 번에 모아 보여 주는 것만으로 처음 쓰는 사람의 시행착오가 크게 줄어듭니다.
- **"알려진 한계"로 적어 둔 것은 언젠가 사용자를 속인다.** 문서에 적었어도 사람은 도우미 함수를 고치고 재계산을 기대합니다. 0.2에서 한계 자체를 없앴습니다.
- **호환성을 지키는 개선이 가능하면 그쪽을 고른다.** 도우미가 없는 경우의 버전 값을 그대로 둔 것이 기존 사용자 캐시를 살렸습니다.

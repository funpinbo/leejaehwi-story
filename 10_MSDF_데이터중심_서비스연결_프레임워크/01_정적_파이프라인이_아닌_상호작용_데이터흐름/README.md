# 정적 파이프라인이 아닌 상호작용 데이터 흐름 — 챗봇에게서 지휘봉을 빼앗기

> **한 줄 요약**: ETL · ELT는 정해진 시간에 정해진 흐름을 도는 **정적 · 결정적 파이프라인**입니다. 챗봇은 사용자 질문마다 필요한 fetch · crawl · 가공이 달라서, 기능을 붙일수록 **챗봇이 오케스트레이터가 되는** 문제가 생겼습니다. 흐름의 기준을 task가 아닌 **데이터(결과물 이름)** 로 바꾸고, 연결은 DAG 파일로 꺼냈습니다.

---

## 1. 상황

- 챗봇을 에이전트로 만들다 보니 검색, 크롤링, 임베딩, 요약 같은 기능이 계속 붙었습니다.
- 데이터 추출 · 가공이 배치 작업이 아니라 **사용자의 검색과 상호작용에 따라 그때그때** 필요했습니다.
- 챗봇은 특히 데이터를 많이 바꾸는 쪽이라, 데이터가 바뀌면 그에 의존하는 기능들이 다시 움직여야 했습니다.

## 2. 문제

| # | 문제 | 증상 |
|---|---|---|
| 1 | **챗봇이 순서를 안다** | "검색 → 임베딩 → 요약"을 챗봇 코드가 직접 부르고 넘김 |
| 2 | **기능끼리 서로를 안다** | 임베딩 서비스가 검색 결과의 위치 · 형식을 알아야 함 |
| 3 | **기능 추가 = 챗봇 수정** | 번역 단계 하나를 넣어도 챗봇 코드가 바뀜 |
| 4 | **정적 도구가 맞지 않음** | Airflow식 스케줄 DAG는 "이 질문에 필요한 것만 지금" 돌리기 어렵고, 같은 질문의 반복을 캐시로 다루지 않음 |

## 3. 대안 비교

- 챗봇 안에 오케스트레이션을 두면, 기능이 늘수록 챗봇이 모든 기능의 순서와 실패 처리까지 알게 됩니다.
- 메시지 큐로 이벤트만 흘리면 서로는 몰라도 되지만, "이 결과가 어떤 입력에서 나왔나"(계보)와 "같은 요청이면 재사용"을 각 서비스가 따로 구현해야 합니다.
- 그래서 **"서비스 사이 데이터 이동의 권한 · 실패 · 추적만 맡는 계층"** 으로 범위를 정했습니다. 서비스 자체를 관리하는 시스템은 만들지 않습니다.

## 4. 해결

```
전:  챗봇 ── search() ──▶ embed() ──▶ refine() ──▶ 답변      (챗봇이 순서 · 실패 · 저장 위치를 앎)

후:  챗봇 ── order("search_result") ──▶ [엔진 + DAG] ──▶ on_search_result()
                                         search → embedding → processing   (서로 모름)
```

- 서비스는 **결과물 이름만** 요청하고(`order`), 결과는 DAG의 `deliveries`가 정한 함수로 도착합니다.
- 각 서비스는 자기 Action의 입력 · 출력 슬롯만 선언합니다. 다른 서비스 이름, 저장 위치, 데이터 ID가 코드에 나오지 않습니다.
- 번역 기능을 넣을 때는 새 서비스를 만들고 **DAG에 노드 하나와 엣지를 더할 뿐**, 챗봇 코드는 바뀌지 않습니다.

## 5. 결과

- 예시 챗봇(검색 → 임베딩 → 가공 → 챗봇)이 서로를 import하지 않고 동작합니다.
- 같은 질문을 다시 하면 세 단계 모두 **실행하지 않고** 저장된 결과로 답합니다.
- 웹 UI의 DAG 편집기로 n8n처럼 노드를 끌어다 연결하면 같은 YAML이 저장됩니다.

## 6. 배운 점

- **흐름의 단위를 무엇으로 잡느냐가 구조를 정한다.** task로 잡으면 순서를 아는 누군가가 필요하고, 데이터로 잡으면 "무엇이 필요한가"만 남습니다.
- **오케스트레이션은 기능이 아니라 별도의 책임이다.** 기능 안에 두면 기능이 늘수록 그 기능이 무거워집니다.
- **범위를 한 문장으로 정해 두면 흔들리지 않는다.** 개발 중 예시 서비스까지 만들려다 멈춘 것도 이 문장 덕분이었습니다.

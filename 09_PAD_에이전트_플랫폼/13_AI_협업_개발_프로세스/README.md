# AI 협업 개발 프로세스 — 기억이 없는 코딩 에이전트와 여러 서비스를 만드는 법

> **한 줄 요약**: AI 코딩 에이전트(Claude Code)는 세션 사이에 기억이 없어서, 서비스가 늘어나자 매번 맥락을 다시 파악하느라 느리고 일관성이 없어졌습니다. 그래서 **"왜 · 무엇을"(드물게 바뀜)과 "지금 당장 무엇을"(계속 버려지고 다시 만들어짐)** 을 분리한 문서 계층을 만들고, 에이전트가 **지금 필요한 한 조각만 읽고 → 실행하고 → 기록하고 → 다음 조각을 고르는** 순환을 hook으로 자동화했습니다. 다음 단계가 사람의 판단이 필요하면 **추측하지 않고 멈춥니다.**

---

## 1. 상황

- 저는 사내 SW 개발 담당으로 설계 · 판단 · 검증을 맡고, 구현은 AI 코딩 에이전트와 함께 진행했습니다.
- 서비스가 여럿이고, 서비스를 가로지르는 작업(TASK)이 여러 개 동시에 진행.
- 문제: 에이전트가 호출될 때마다 프로젝트 전체 역사를 다시 읽어야 했고, 같은 결정을 다르게 다시 내리는 일이 생겼습니다.

## 2. 설계 — 문서 계층

| 문서 | 범위 | 수명 | 답하는 질문 |
|---|---|---|---|
| `plan` | 서비스 / 프로젝트 | 드물고 신중하게 바뀜 | 설계는 무엇이고 **왜** 그런가? |
| `rule` | 서비스 / 프로젝트 | 드물게 바뀜 | 모든 변경이 지켜야 하는 제약은? |
| `prompt` 큐 | 서비스 | 영구 · 누적 | 사람이 **자기 말로** 무엇을 요청했나? |
| `log` | 서비스 | 영구 · 누적 | 무엇을 끝냈고 **어떻게 확인**했나? |
| **`task`** | 서비스 횡단 | task 종료까지 | 지금 끝내려는 것과 서비스별 분담은? |
| **long-term memory** | 서비스 · 현재 task | task 종료 / plan 변경까지 | 이 서비스가 할 일 목록(순서 · 완료 기준)은? |
| **short-term memory** | 서비스 | 지금 항목 종료까지 | **지금 당장** 무엇을 하는가? |

- 가장 중요한 구분: **plan을 바꾸는 것은 기록할 가치가 있는 결정**이고, long-term memory를 다시 쓰는 것은 그 plan을 실행하기 위한 오늘의 체크리스트일 뿐 — 계속 바뀌는 게 정상입니다.
- short-term memory는 항상 **세 상태 중 정확히 하나**: `지금 할 일` / `비어 있음` / `막힘 — 사람의 결정 필요`

## 3. 실행 순환

```
1. 에이전트는 해당 서비스의 short-term memory만 읽는다 (plan 전체 X, 목록 전체 X)
2. 그 한 가지를 수행한다
3. 끝나면: log에 결과·확인 방법 append → task에 한 줄 진행 → short-term을 "비어 있음"으로
4. 턴 종료 hook이 판단한다
   - long-term에 남은 항목 → 다음 항목을 "지금 할 일"로
   - long-term 소진       → 이 서비스 몫을 task에서 완료 처리
   - 다음 단계가 사람 판단 필요 → "막힘"을 쓰고 멈춤 (할 일을 지어내지 않는다)
5. 모든 관련 서비스가 완료하면 task 종료
```

- hook은 "파일이 있나"가 아니라 **"다음이 무엇인가"를 판단**해야 해서, 스크립트가 아니라 작은 **agent 타입 hook**으로 구현했습니다.
- **라우팅 skill**: 요청이 들어오면 먼저 "실제로 처리할 서비스가 어디인가"를 판단 (증상이 보인 서비스가 원인 서비스가 아닐 때가 많음). 작은 수정은 바로 처리, 서비스 횡단 · 다단계는 memory cycle로.

## 4. 실제로 돌았던 작업

| TASK | 관련 서비스 | 결과 |
|---|---|---|
| TASK-1: 서비스 간 호출을 선언형 Control Plane으로 이전 | 다수 | 4단계 전환 완료, 안전망 제거 단계의 운영 사고를 log로 기록 → [10번 경험](../10_Control_Plane_단계적_전환과_운영사고) |
| TASK-2: PDF/DOCX 렌더 출력 + 서식 DSL을 정규식으로 설명한 프롬프트 수정 | 2개 | 테스트 통과 + 실제 렌더 요청으로 확인 후 완료 → [01번 경험](../01_LLM은_판정하지_않는다_결정적_STEP) |

log 항목은 "끝났다"가 아니라 **"어떻게 확인했는가"** 까지 적어야 완료로 인정했습니다. (예: "전체 테스트 통과 수 · 배포 후 운영 로그에서 오류 없음 확인")

## 5. 배운 점

- **AI 에이전트의 생산성은 "무엇을 읽게 하느냐"로 결정된다.** 전부 읽히면 느리고 흔들리고, 지금 필요한 한 조각만 읽히면 빠르고 일관됩니다.
- **결정과 할 일을 다른 문서에 둔다.** 그래야 "왜 이렇게 했지?"와 "다음에 뭘 하지?"가 섞이지 않습니다.
- **멈출 줄 아는 자동화가 믿을 수 있는 자동화다.** PAD 에이전트가 근거 없으면 추측하지 않고 "미확정"으로 남기듯, 개발 순환도 사람 판단이 필요한 지점에서 멈추게 했습니다.
- **사람의 역할은 설계 · 판단 · 검증으로 옮겨 간다.** 코드를 직접 다 치지 않아도, 무엇을 만들지 정하고 결과를 검증하는 책임은 그대로 저에게 있습니다.

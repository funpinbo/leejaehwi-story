# LLM은 판정하지 않는다 — 결정적 단계 파이프라인

> **한 줄 요약**: PAD 작성 과정을 여러 단계로 나누고, 단계마다 **LLM을 쓸지 말지, 쓴다면 무엇까지 맡길지**를 정했습니다. LLM은 분류(닫힌 선택지) · 요약 · 후보 추천 · 값 추출만 하고, 코드 확정 · 규격 계보 · 품질 등급 같은 **판정은 코드와 승인된 테이블이 결정**합니다. 결과는 모든 필드에 **값 + 근거 + 상태**가 붙은 "슬롯 JSON"입니다.

---

## 1. 상황

- 처음 문서 AGENT를 만들 때는 "LLM이 PAD 내용을 써준다"는 그림이었습니다.
- 하지만 PAD의 핵심 항목(사내 부품 코드, 적용 규격과 그 개정 계보, 품질 등급)은 **틀리면 승인 문서가 반려**되는 값입니다.

## 2. 문제

| LLM에게 맡겼을 때 | 결과 |
|---|---|
| 사내 코드 "확정" | 형식은 맞는데 테이블에 없는 코드를 만들어냄 |
| 규격 계보 판단 | 그럴듯한 상위 규격을 기억으로 채움 |
| 품질 등급 | 같은 입력에 다른 답 (재현 불가) |

## 3. 설계 — 단계별 LLM 사용 범위

| 단계 | 하는 일 | 판정 방식 | LLM |
|---|---|---|---|
| 입력 파싱 | 사용자 입력 · BOM 정규화 | 정규식 | X |
| 부품 분류 | 부품 유형 분류 | **닫힌 선택지** 중 하나만 허용 | O 분류 |
| 데이터시트 요약 | 근거 문서 요약 | 승인된 지식 → 공식 출처 → 웹 검색 순 | O 요약 |
| 사내 코드 확정 | 코드 결정 | LLM이 **후보**를 내면 코드 테이블 조회로 **확정** | O 후보만 |
| 규격 계보 | 적용 규격과 개정 관계 | 근거 문장에서 규격 번호 추출 → **승인된 관계만** 대조 | X (금지) |
| 품질 등급 | 등급 파생 | 규칙(조건문) | X |
| 검사 · 시험 | 시험 항목 결정 | 표준 원문 우선, 없으면 전례 | O 값 추출만 |
| 메타데이터 | 문서 관리 정보 | 규칙 | X |
| 최종 승인 · 서명 | — | **사람** (자동화 범위 밖) | X |

**슬롯 JSON** — 모든 필드는 같은 모양입니다.

```json
{"field": "part_code", "value": "...", "status": "CONFIRMED | CANDIDATE | MISSING",
 "evidence": [{"source": "code_table", "ref": "..."}], "decided_by": "rule | table | llm_candidate"}
```

- `status`가 `CANDIDATE`나 `MISSING`이면 사람이 확인해야 하는 칸이라는 뜻이고, 화면에도 그렇게 보입니다.
- **값이 없으면 비워 둡니다.** 그럴듯한 값을 채우지 않는 것이 개발 표준 원칙("가짜 데이터를 보여주지 않는다")입니다.

## 4. 함께 정한 규칙

- 규격 관계는 **후보 → 승인/반려** 게이트를 거치고, 규격 계보 단계는 `approved`만 사용합니다.
- 사내 코드는 정규식이 아니라 **자체 DSL**로 정의돼 있었는데, 필드 생성 프롬프트가 이를 "표준 정규식"이라고 설명하고 있었습니다. 이 DSL에서 `[0]`은 **"숫자 1자리"**인데 정규식에서는 **"문자 0"** 이라 뜻이 정반대였고, 모델이 정확히 틀린 모양의 값을 만들어 서식 검증에서 대량으로 걸렸습니다.
  - 사용자 보고("형식과 일치하지 않음 오류 — 프롬프트 문제 같다")에서 실제 프롬프트 문장까지 근본 원인을 추적
  - 프롬프트를 실제 DSL 문법으로 고치고, 같은 작업에서 DOCX로 하드코딩돼 있던 출력 형식을 PDF/DOCX 선택으로 연결
  - 완료 판정 전 검증: 백엔드 테스트 통과 + 실제 렌더 요청으로 **두 형식 모두 올바른 파일이 생성되는지** 확인
  - 이후 "프롬프트·코드에서 사내 표기법을 정규식이라고 표현 금지"를 개발 표준에 명시
- 검색 그래프(파싱~요약)와 작성 그래프(코드 확정~메타데이터)를 나누고, 그 사이를 **LangGraph 체크포인트**로 이어서, 사람이 데이터시트를 확인한 뒤 작성을 이어갈 수 있게 했습니다.

## 5. 결과

- 판정 단계는 **같은 입력이면 항상 같은 결과**가 나옵니다.
- 사람은 전체를 검토하지 않고, `CANDIDATE` / `MISSING` 상태인 칸만 확인하면 됩니다.

## 6. 배운 점

- **LLM 시스템 설계의 핵심은 "LLM을 어디에 쓰지 않을 것인가"를 정하는 것이다.** 사용 범위를 단계 단위로 표로 만들자 리뷰와 테스트가 쉬워졌습니다.
- **후보와 확정을 분리한다.** LLM은 검색 공간을 줄이는 데 쓰고, 마지막 결정은 검증 가능한 데이터가 내립니다.
- 06에서 "형식은 코드가"로 시작한 원칙이 여기서 **"판정은 코드가"** 로 넓어졌습니다.

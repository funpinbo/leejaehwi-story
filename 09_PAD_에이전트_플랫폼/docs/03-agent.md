# 챗봇/문서 에이전트

LangGraph 기반이다. 서로 연관되지만 구분되는 두 흐름이 같은 evidence/state 메커니즘을 공유한다: 일반 기술 Q&A 채팅과, 구조화된 다중 필드 문서 생성 파이프라인.

## 왜 근거 수집이 한 번의 검색이 아니라 루프인가

이 도메인 특유의 두 가지 구조적 이유로, 기술 표준 코퍼스에 대한 한 번의 벡터 검색만으로는 실제 질문에 답이 안 되는 경우가 많다:

- 표준 문서는 실제 시험 절차를 다시 쓰는 대신 다른 표준을 **참조**하는 경우가 흔하다("[다른 표준]의 Method 1014에 따라"). 사용자가 물어본 그 문서만 보는 검색은 그 문서가 의존하고 있는 내용을 놓친다.
- 질문은 보통 여러 하위 질문(예: 적용 표준, 스크리닝 요구사항, lot-acceptance 시험, 방사선 요구사항)으로 쪼개지고, 각각 자기만의 타겟 검색이 필요할 수 있다 — 한 번의 넓은 검색은 가장 관련된 문서의 가장 일반적인 최상위 섹션만 가져오고 task-specific한 내용은 못 가져오는 경향이 있다.

그래서 research 경로는 경계가 있는 루프다: 질문 분류 → 부품 번호와 관련 표준 family 식별 → task 목록 작성 → task마다 우선순위가 매겨진 소스 순서(내부 지식 그래프 → 등록/공식 문서 → 웹)로 검색 → 가져온 문서가 아직 evidence tree에 없는 자식 표준을 참조하면 그것도 가져오기(깊이/라운드 상한이 무한 확장을 막음) → 모은 근거가 필요한 사실을 실제로 커버하는지 평가 → 답변하거나, 경계가 있는 재검색을 한 라운드만 더 한다.

## 환각이 비용이 큰 지점에서의 Closed-set 판정

파이프라인의 몇 단계는 LLM이 관여하긴 하지만 "LLM에게 물어보고 그 출력을 믿는다"는 식으로 짜여 있지 **않다**:

- **부품/family 분류**는 규칙 엔진 자신의 테이블에 실제로 존재하는 값들로 닫힌 집합으로 제약된다 — 모델이 값을 제안할 수는 있지만, 그 집합 밖의 값은 regex/lookup 체크가 (받아들이지 않고) 거부한다. 그래서 모델이 존재하지 않는 분류 코드를 지어낼 수 없다.
- **"이 표준이 이 부품군에 적용되는가"**는 LLM 판단이 아니라 curated된 적용성 edge에 대한 DB join으로 답한다 — 확인되지 않은 관계는 독자에게 "확인 안 됨"으로 드러나고, 조용히 "아니오"로 처리되거나 추측으로 덮이는 일이 절대 없다.
- 원본 문서로부터의 숫자/식별자 추출은 생성 후 원문 텍스트와 그대로 대조된다; 인용된 근거에 그대로 나타나지 않는 값은 사실로 제시되지 않고 플래그된다.

이 아래 깔린 원칙은 프로젝트 초기에 명시됐고 그 뒤로 계속 집행됐다: 불완전하지만 정직하게 플래그된 답변이, 추측 위에 세워진 완전해 보이는 답변보다 낫다 — 이 결과물은 사람이 감사할 수 있어야 하는 안전/규정준수 문서이고, 확신에 찬 오답이 명백히 불완전한 답보다 엄격히 더 나쁘기 때문이다.

# 트러블 슈팅

## Evidence 점수 오류

진짜 유사도 검색(내부 코퍼스에 대한 vector search, 이전에 승인된 답변 캐시, 승인된 외부 참조)에서 수집된 근거는 실제 관련도 점수 — 이 소스들 전체에 일관되게 계산되는 코사인 유사도 — 를 갖는다. 자연스러운 유사도 숫자가 없는 소스(웹 검색 hit, 구조화 DB 조회, 규칙엔진 카탈로그 매치)의 근거는 **가짜 점수를 받지 않는다**. 예전 버전의 코드는 "랭킹 코드를 단순하게 유지하려고" 이런 근거 전부에 상수 `1.0`을 찍었다 — 이는 질문이 (흔한 경우인) 진짜 vector-search 근거와 다른 소스를 섞을 때마다, 그 상수 `1.0`이 최종 답변에 들어갈 근거 양을 제한하는 cutoff에서 항상 진짜 유사도 점수를 이겨버린다는 뜻이었다. 수정은 "진짜 유사도 신호가 없음"을 1급 상태로 취급한다(sentinel 값이 아니라 그 필드가 단순히 없는 것으로) — 그리고 특정 하위 task에 속한다고 명시적으로 태그된 근거에 이미 적용되던 것과 같은 처리를, 이런 근거에도 똑같이 적용해 유사도 기반 cutoff에서 완전히 면제한다. 

## state와 input 오류

LangGraph의 state 객체는 append-only reducer가 없는 flat dictionary다 — 노드가 반환한 key는 그 턴의 이전 값을 그냥 덮어쓰므로, 한 턴 안에서는 노드를 거칠수록 state가 구조적으로 무한히 커지지 않는다. 증가가 실제로 나타난 곳은 **턴을 가로지르는** 부분이었다: 어떤 턴의 라우팅이 설정한 체크포인트된 필드를, 다르게 라우팅된 나중 턴의 코드 경로가 전혀 건드리지 않으면, 그 필드는 (리듀서 없는 TypedDict 기반 state에 대한 체크포인터의 정상 동작으로서) 이전 턴의 낡은 값을 그대로 유지한다. 이런 종류의 누수 2건이 실제로 발견·수정됐다: 이전의, 부품에 특화된 질문의 부품-식별 아티팩트가 나중의, 무관한 질문의 답변 메타데이터로 그대로 살아남은 것; 그리고 이전 턴에서 감지된 부품-변형(variant) 경고가, 나중 턴의 실제 research가 그런 걸 전혀 못 찾았는데도 그 나중 턴의 답변 프롬프트에 무조건 덧붙여진 것. 수정은 "원래 이걸 지워줬을 노드가 돌았다"에 의존하는 대신, 지워야 할 모든 필드를 명시하는 턴 시작 시점의 리셋이다.

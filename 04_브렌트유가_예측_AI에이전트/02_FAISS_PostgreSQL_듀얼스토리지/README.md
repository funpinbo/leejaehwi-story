# FAISS + PostgreSQL 듀얼 스토리지 — 찾는 저장소와 증명하는 저장소

> **한 줄 요약**: 원문 임베딩만으로는 "이 뉴스 유형과 유가의 상관관계" 같은 메타데이터를 함께 다루기 어려워서, **의미 검색은 FAISS(VDB)**, **상관관계·속성·근거 추적은 PostgreSQL(RDB)** 에 나눠 저장하고 `doc_id`로 연결했습니다.

---

## 1. 상황

- Event Study로 뉴스 클러스터마다 "유가에 준 영향(CAR)", "사건일", "출처" 같은 **정형 메타데이터**가 생겼습니다.
- 에이전트는 "최근 공급 차질 뉴스가 과거에 유가를 어떻게 움직였나?" 같은 질문에 답해야 했습니다.

## 2. 문제

| 저장 방식 | 한계 |
|---|---|
| 벡터 DB만 사용 | 의미 검색은 잘하지만, 숫자 조건 필터·집계·조인이 어렵고 "왜 이 문서가 나왔는지" 추적이 어려움 |
| RDB만 사용 | 정확한 조회는 잘하지만, "의미가 비슷한 뉴스"를 찾을 수 없음 |

## 3. 설계

```
           ┌──────────── doc_id ────────────┐
[FAISS]  원문 임베딩                     [PostgreSQL]
         "의미가 비슷한 뉴스 찾기"          news(doc_id, date, source, cluster_id, text)
                                          cluster_effect(cluster_id, car, n_events)
                                          query_log(question, doc_ids, answer)  ← 근거 추적
```

- **검색 흐름**: 질문 임베딩 → FAISS Top-K `doc_id` → PostgreSQL에서 `doc_id`로 조인해 날짜·클러스터 영향·출처를 가져옴 → LLM 컨텍스트
- **로그**: 어떤 질문에 어떤 문서가 쓰였고 어떤 답이 나왔는지 SQL로 다시 조회 가능 → 금융 도메인에서 필요한 **설명 가능성** 확보

## 4. 결과

- 에이전트의 DB Tool 하나가 "의미 검색 + 정형 메타데이터"를 함께 반환하게 되어, 답변에 **수치 근거와 출처**를 붙일 수 있게 되었습니다.

## 5. 배운 점

- **저장소는 "어떻게 꺼낼 것인가"로 고른다.** 의미로 꺼낼 데이터와 조건으로 꺼낼 데이터는 저장소가 달라야 했습니다.
- **트레이드오프를 알고 선택한다.** 규모가 작다면 pgvector로 단일 DB가 더 단순합니다. 이 프로젝트에서는 각 컴포넌트를 명확히 분리해 이해하는 것도 목표였기 때문에 분리했습니다.
- 이 "근거 추적 가능한 저장" 원칙은 이후 ECSS 그래프DB 프로젝트의 `source_region_id`(원본 PDF 영역 역추적)로 이어졌습니다.

# Hallucination 회고 — 해결하지 못한 문제를 기록하는 법

> **한 줄 요약**: LLM이 근거 없는 수치를 만들거나 전문가가 납득하기 어려운 "그럴듯한 문장"을 생성하는 문제를 프로젝트 기간 안에 완전히 해결하지 못했고, 회고를 통해 **"도메인 이해 → 강한 CoT 유도 → 출력 검증"** 순서라는 다음 설계 원칙을 얻었습니다.

---

## 1. 상황

- 에이전트가 최종 답변을 쓸 때, Tool이 가져온 데이터에 **없는 수치**를 만들어 넣는 경우가 있었습니다.
- 수치가 맞더라도 유가 시장 전문가가 보기에 **인과 관계가 어색한 문장**이 나왔습니다.

## 2. 프로젝트 기간 중 시도

| 시도 | 효과 | 한계 |
|---|---|---|
| "컨텍스트에 없는 내용은 답하지 말라" 지시 | 일부 감소 | 수치를 "추정"이라며 계속 생성 |
| Temperature 낮추기 | 표현 변동 감소 | 근거 없는 수치 자체는 남음 |
| Tool 결과를 프롬프트 앞부분에 배치 | 일부 개선 | 긴 컨텍스트에서 다시 발생 |

## 3. 왜 해결하지 못했나 (원인 분석)

1. **도메인 학습이 프롬프트 설계보다 늦었다.** 유가 시장에서 어떤 인과가 "말이 되는지" 팀이 충분히 몰랐기 때문에, LLM에게 어떤 추론 단계를 거치게 해야 하는지 정의하지 못했습니다.
2. **추론 과정을 강제하지 않았다.** 결론만 요구하니 모델이 중간 근거 없이 그럴듯한 문장으로 바로 갔습니다.
3. **출력을 검증하는 단계가 없었다.** 생성된 수치가 Tool 결과에 실제로 있는지 확인하지 않았습니다.

## 4. 회고에서 얻은 다음 설계 원칙

```
① 도메인 학습 선행     : 전문가가 "말이 된다"고 보는 추론 경로를 먼저 정리
② 강한 CoT 유도       : 근거 데이터 → 해석 → 결론 순서를 출력 형식으로 강제
③ 출력 검증(grounding) : 답변의 수치가 컨텍스트에 있는지 코드로 확인, 없으면 재생성/표시
④ 형식이 있는 출력은 구조화 : 자유 문장 대신 JSON 스키마
```

이 원칙은 실제로 이후 프로젝트에 적용됐습니다.

| 원칙 | 적용된 곳 |
|---|---|
| 형식은 코드가, 내용만 LLM이 | [06. 문서 AGENT — Content/Layout 분리](../../06_MID_문서형식유지_작성AGENT) |
| 출력을 그대로 믿지 않음 | [07. ECSS — `confidence`, `requires_review` 스키마](../../07_MID_ECSS규격_그래프DB_파이프라인) |
| 기법을 맹신하지 않고 청중에 맞게 평가 | [08. 사내 교육 — 기법별 실효성 평가](../../08_MID_사내_프롬프트엔지니어링_교육) |

## 5. 배운 점

- **해결하지 못한 문제도 원인을 정리하면 자산이 된다.** "안 됐다"에서 멈추지 않고 "왜 안 됐는지"를 정리한 것이 이후 프로젝트의 설계 기준이 되었습니다.
- **Hallucination은 프롬프트 한 줄의 문제가 아니라 시스템 설계의 문제.** 생성 → 검증 → 재시도의 루프가 있어야 합니다.

## 🧪 예제 코드 — `numeric_grounding.py`

회고에서 도출한 ③ **출력 검증**을 구현한 예제입니다.
LLM 답변에서 수치를 추출해 Tool 결과(컨텍스트)에 존재하는지 확인하고, 근거 없는 수치를 표시합니다.

```bash
python numeric_grounding.py
```

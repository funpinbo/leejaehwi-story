# 기법별 실효성 평가와 Skill — 유행이 아니라 청중 기준으로 고르기

> **한 줄 요약**: 페르소나 · CoT · ReAct · MCP · Skill 5가지 기법을 단순 소개하지 않고, **"비개발자 비중이 큰 우리 회사 직원에게 실제로 효과가 있는가"** 를 기준으로 각각 평가해 권장 수준을 다르게 제시했고, 가장 권장한 Skill은 PAD 업무용 3종을 직접 설계해 보여줬습니다.

---

## 1. 상황

- 프롬프트 기법은 매달 새로 나오고, 어떤 기법은 최신 연구에서 효과가 줄었다는 결과도 나옵니다.
- 모든 기법을 나열하면 청중은 무엇을 써야 할지 모릅니다.

## 2. 평가 기준

- 대상: **비개발자 비중이 큰 전 직원**
- 질문: "이 기법을 내일 업무에 바로 쓸 수 있는가? 쓰면 효과가 있는가?"
- 자료: **2026년 4월 이후 최신 자료** 기준으로 각 기법이 여전히 유효한지 재검증

## 3. 기법별 판단

| 기법 | 판단 | 근거 |
|---|---|---|
| **페르소나** | 입문용으로 **유지** | 성능 저하 근거가 있다는 것을 알지만, 프롬프트가 낯선 사람에게 "역할부터 정해주기"는 여전히 좋은 출발점 |
| **CoT** | 일반 사용자에게 **효과적** | 에이전트 설계보다는, 일반 사용자가 "순서대로 생각하게" 하는 데 여전히 유효 → PAD 검토 절차로 시연 |
| **ReAct** | **대안적 활용법** 제시 | 직접 구조를 설계하는 부담이 큼 → "AI에게 먼저 프롬프트화를 시킨 뒤 질문하기"로 우회 |
| **MCP** | **강조** | GUI로 제공되는 경우가 늘어 비개발자도 쓸 수 있음 → Notion 등에 정리시키는 활용법 권장 |
| **Skill** | **가장 적극 권장** | ReAct 절차를 강제하고, 매번 프롬프트를 새로 쓸 필요가 없고, AI가 Skill을 직접 만들 수도 있음 |

## 4. Skill 3종 설계 (PAD 업무)

| Skill | 하는 일 |
|---|---|
| [`ecss-spec-check`](./skills/ecss-spec-check/SKILL.md) | 부품 종류로 적용 ECSS/ESCC 규격 후보를 찾고 근거 조항을 인용 |
| [`spec-revision-check`](./skills/spec-revision-check/SKILL.md) | 인용한 규격의 Revision이 최신인지 확인, 불확실하면 확인 요청 |
| [`pad-format-finalize`](./skills/pad-format-finalize/SKILL.md) | 작성 내용을 PAD 템플릿의 placeholder JSON으로 확정 |

Skill 하나가 "절차 + 근거 + 출력 형식"을 고정해 주기 때문에, 사용자는 **"PAD 작성해줘"** 한 줄만 쓰면 됩니다.

## 5. 결과

- 청중이 기법 이름이 아니라 **"내 업무에 무엇을 쓰면 되는지"** 를 가져감
- Skill 3종은 [06. 문서 AGENT](../../06_MID_문서형식유지_작성AGENT)의 Report / Verification / Layout 역할과 같은 구조라, 교육과 실제 개발이 같은 설계 언어를 공유

## 6. 배운 점

- **기법을 맹신하지 않는다.** 논문 결과와 실제 청중의 상황을 함께 보고 판단해야 합니다.
- **좋은 교육은 "무엇을 하지 않아도 되는지"도 알려준다.** ReAct를 직접 설계하라고 하지 않고 대안을 준 것이 비개발자에게 가장 반응이 좋았습니다.
